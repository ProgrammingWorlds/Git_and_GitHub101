MODULE 10 · LESSON 10.3

Reset, reflog and common errors

Reset وreflog والأخطاء الشائعة

Learning objectives

  • Explain soft, mixed and hard reset.
  • Recover with reflog.
  • Fix five common errors.

Prerequisites

Lesson 10.2.

Introduction

Reset moves your branch backwards. It is powerful, so learn its three modes.

Explanation

git reset --soft HEAD~1 undoes the last commit but keeps the changes staged.

git reset HEAD~1 (mixed, the default) keeps the changes in files but unstaged.

git reset --hard HEAD~1 undoes the commit and discards the changes. Use it only on local work you do not need.

Never reset commits you already pushed; use revert.

git reflog lists where HEAD has been, including commits that look lost. Use git reset --hard ID or git switch -c rescue ID to get back (Figure 1). Reflog is local and entries expire after some weeks.

Common errors. “Author identity unknown” → set user.name and user.email. “not a git repository” → cd to the project. “nothing to commit” → nothing changed or not staged. “failed to push some refs … fetch first” → git pull then push. “detached HEAD” → git switch main (or git switch -c name to keep the work).

Real-world analogy

Soft, mixed and hard are three depths of rewinding a tape: keep everything ready, keep the edits, or erase.

Common mistakes and solutions

Using --hard casually.Prefer soft or mixed.
Resetting pushed commits.Use revert.
Giving up on lost commits.Look in reflog first.

Practical exercise

Make a test commit, undo it with reset --soft, then recommit.

Expected result

The file is staged again after reset --soft.

Knowledge check

1. Which reset keeps changes staged?
2. How do you find a “lost” commit?
3. “fetch first” on push means…

Answers

  • --soft — Soft keeps them staged.
  • git reflog — It records HEAD moves.
  • Pull before pushing — GitHub has newer commits.

Summary

Reset rewinds locally, reflog rescues, and revert is for shared history.
