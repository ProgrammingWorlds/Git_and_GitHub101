الوحدة 10 · الدرس 10.3

Reset وreflog والأخطاء الشائعة

Reset, reflog and common errors

أهداف التعلم

  • أن تشرح soft وmixed وhard.
  • أن تتعافى بـ reflog.
  • أن تصلح خمسة أخطاء شائعة.

المتطلبات المسبقة

الدرس 10.2.

مقدمة

الـ reset يرجّع فرعك إلى الخلف. هو قوي، فتعلّم أنماطه الثلاثة.

الشرح

git reset --soft HEAD~1 يلغي آخر commit ويُبقي التغييرات في staging.

git reset HEAD~1 (mixed وهو الافتراضي) يُبقي التغييرات في الملفات لكن خارج staging.

git reset --hard HEAD~1 يلغي الـ commit ويرمي التغييرات. استخدمه فقط على عمل محلي لا تحتاجه.

لا تعمل reset لـ commits رفعتها؛ استخدم revert.

git reflog يسرد أماكن HEAD بما فيها commits تبدو ضائعة. استخدم git reset --hard ID أو git switch -c rescue ID للعودة (الشكل 1). الـ reflog محلي وتنتهي مدة إدخالاته بعد أسابيع.

أخطاء شائعة. «Author identity unknown» ← اضبط user.name وuser.email. «not a git repository» ← cd إلى المشروع. «nothing to commit» ← لا تغيير أو لم يُضف. «failed to push some refs … fetch first» ← git pull ثم push. «detached HEAD» ← git switch main (أو git switch -c name للاحتفاظ بالعمل).

تشبيه من الحياة

soft وmixed وhard ثلاثة أعماق لإرجاع شريط: أبقِ كل شيء جاهزًا، أو أبقِ التعديلات، أو امسح.

مخطط توضيحي

الأوامر

git reset --soft HEAD~1
git reset HEAD~1
git reflog
git reset --hard ID

الخيار --hard مدمّر للعمل غير المحفوظ.

أخطاء شائعة وحلولها

استخدام --hard بخفة.فضّل soft أو mixed.
عمل reset لـ commits مرفوعة.استخدم revert.
اليأس من commits ضائعة.انظر في reflog أولًا.

تمرين عملي

نفّذ commit تجريبيًا وألغِه بـ reset --soft ثم أعد الحفظ.

النتيجة المتوقعة

الملف في staging من جديد بعد reset --soft.

اختبر فهمك

1. أي reset يُبقي التغييرات في staging؟
2. كيف تجد commit «ضائعًا»؟
3. «fetch first» عند الرفع تعني…

الإجابات

  • --soft — الـ soft يُبقيها في staging.
  • git reflog — يسجّل حركات HEAD.
  • اسحب قبل الرفع — عند GitHub commits أحدث.

الخلاصة

الـ reset يرجّع محليًا، والـ reflog ينقذ، والـ revert للتاريخ المشترك.

مصطلحات أساسية

resetنقل الفرع إلى commit آخر
reflogسجل حركات HEAD
detached HEADHEAD على commit لا على فرع
