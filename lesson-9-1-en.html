MODULE 09 · LESSON 9.1

The branch-and-push workflow

سير العمل بالفروع

Learning objectives

  • Describe the team workflow.
  • Create and push a feature branch.
  • Know collaborators versus forks.

Prerequisites

Modules 7 and 8.

Introduction

Teams never commit straight to main. They work on branches and propose changes.

Explanation

Workflow. Update main, create a branch, commit, push the branch, open a pull request, get a review, merge, then clean up (Figure 1).

Start every task with git switch main and git pull so your branch starts from the latest work.

Create the branch: git switch -c feature/about-page. Use short, clear names: feature/…, fix/…, docs/….

Commit small, focused changes with clear messages.

Publish: git push -u origin feature/about-page. GitHub then shows a yellow banner with Compare & pull request.

Collaborator. The owner invites you under Settings → Collaborators. You can push branches to the same repository.

Fork. If you are not a collaborator, you click Fork to make your own copy, push there, and open a pull request to the original. Forks are how open-source contributions work.

Real-world analogy

You write your chapter in a separate document and hand it to the editor. The editor decides when it joins the book.

Common mistakes and solutions

Branching from an old main.Pull main first.
Huge branches with many unrelated changes.One purpose per branch.
Pushing to main on a protected repository.Push a branch instead.

Practical exercise

Create feature/about-page, add about.html, commit, and push it.

Expected result

GitHub lists the branch and offers Compare & pull request.

Knowledge check

1. Where do teams commit new work?
2. What does -u do in the push?
3. When do you fork?

Answers

  • On a branch — Branches protect main.
  • Sets the upstream — Later you can just git push.
  • You cannot push to the original — Contributors use forks.

Summary

Pull main, branch, commit, push the branch. Forks are for outside contributors.
